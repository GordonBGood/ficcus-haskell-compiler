# H21 notes: Powersort for List and Vector (branch feat/sort)

Step 0 (read only):
1. Before H21, `List.sort` was elm/core's `sortBy identity`; in the C path `overlay/FicOverlay.elm` redirected `sortBy` and `sortWith` (Ficcus.Mono.Overlay table) to Elm code: keys computed once into `(key, x)` pairs, then a stable top down merge sort on lists (`sortN`, `mergeLists`). No kernel.
2. `compare` is the kernel `Basics.compare` in `Ficcus.Mono.CGen`: Int and Float are inline expressions (Order: LT 0, EQ 1, GT 2; a NaN gives GT); every other exact type uses a generated structural helper `fic_cmp_N` (tuples, lists; String is `fic_str_cmp`). There is no runtime-wide generic compare; it is generated per exact type (`cmpExpr`, `HCmp`).
3. A closure is called with `fic_ap2(f, mask, w0, w1)` (runtime/fic_closure.h): `f` borrowed, the arguments consumed, every value a `fic_word` (a struct goes boxed), an Order comes back as `.b`.
4. The Vector overlay is `overlay/Vector.elm` (kernel functions have their name as body, types only). A kernel is added in 4 places: that file, `vectorKernels` (name, arity, ownership string) and `updateKernels` in Ficcus.Mono.Kernel, the case in `CGen.vectorCall`, the C function in runtime/fic_vector.h (here fic_sort.h).
5. Elements are flat in the vector: RAW (Int, Float, Char, Bool and structs of them, desc NULL), REF (one pointer), MAP (struct with pointer map). A List of Int is not boxed per element: the cell object holds the Int in its head field (`boxedClass`), so `Vector.fromList` copies n values and `toList` allocates n cells.

Design as built: runtime/fic_sort.h (Powersort core, always_inline, specialised per element size and comparator). Kernels `Vector.sort` (modes I64, F64, U32 and CMP; STRING and GENERIC both go through the generated comparator, String being `fic_str_cmp`), `Vector.sortPerm` (stable permutation of keys: (key, index) pairs for Int, Float, Char keys, an indirect compare otherwise) and `Vector.sortIdx` (indices sorted by a closure comparator). `sortBy` is `permute v (sortPerm (map f v))`: n key calls (a known difference from Elm's JS, documented in the code); `sortWith` is `permute v (sortIdx (\i j -> cmp (get i) (get j)) [0..n-1])`, so the closure comparator receives borrowed elements through Elm code, which the Rc pass dups where the user function consumes them, and struct elements need no boxing in the kernel. `List.sort*` = `Vector.toList (Vector.sort* (Vector.fromList xs))` in the overlay (C path only). Limitation: FicOverlay now imports `Vector`, so a project module named `Vector` (which wins over the overlay) would break every C build of that project; not hit by any test so far.
