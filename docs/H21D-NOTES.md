# H21d notes: List.sortWith speed

Profile (perf, 1M random Int, `List.sortWith compare`, before: 165 ms steady): fic_ap2 24%, the wrapper lambda `\i j -> cmp (get i) (get j)` 21%, the `compare` entry 8%, the sort core 28% (index indirection and branch mispredictions), gen 8%, free 5%. So (a) the closure calls (two levels, one in the wrapper and one for the user's function) are about half; (b) the index indirection is about a fifth; (c) the rest is small.
Experiment (targets/sort/bench_sortwith.c, kernel only, ms): direct elements + closure 88; index + two closures (what sortWith did) 124; index with inline compare 75; direct with inline compare 55. So direct sorting saves about 36 ms (b) and a single closure level another part of (a); the closure call itself costs about 33 ms over an inline compare.

Kept (step 2): `Vector.sortWith` is now a kernel that sorts the elements themselves (no index vector, no gather, one closure level): a generated per-class test (`fic_vsw_N`) copies the two elements out, dups their references (the closure consumes its arguments), boxes a struct as the closure ABI wants, and calls fic_ap2. The core is instantiated with a constant element size 8 and 16 (a call with a variable size made memcpy/memmove library calls: 23% of the time). 165 -> 103 ms. Stability and the no-out-of-bounds guarantee are those of the core; tests: runtime/test_sort.c (stable, in place, inconsistent comparator keeps a permutation), sortdiff.py (rc, no-rc, ASan).

Not built (step 3, a known comparator inlined into the sort core). Options and sizes:
1. A call-site intrinsic: CGen sees `Vector.sortWith f v` with `f` a known clone (a top level function or a lifted lambda) and emits a static copy of the always-inline Powersort core whose test calls the clone directly (the Order compared with 2). About 90 lines in CGen.vectorCall plus a helper, BUT List.sortWith reaches Vector.sortWith through the overlay function `listSortWith cmp xs`, where `cmp` is a parameter, so the comparator is unknown there.
2. To make it known for List.sortWith as well, `List.sortWith` itself must become an intrinsic (kernel id redirect to a kernel with a list argument, the generator doing fromList, sort, toList around the inlined core) about 40 more lines, or the specializer must clone `listSortWith` per known function argument (a new specializer feature, several hundred lines).
3. Expected gain from the experiment: 88 -> 55 ms for the sort itself (about 33 ms of 103). Recommended as a separate step: option 1 plus the List.sortWith intrinsic (about 130 lines).
