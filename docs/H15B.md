### Findings
1. **A `Vector` inside a record that is updated is copied at every step** (`{ q | list = Vector.set q.back x q.list }`): the field read keeps a second owner, `vec_copy` = one per step, 4.2 s at 10^6 (quadratic). A record pattern in a function head is refused (extensible record, row polymorphism slice 5 not done). A custom type `Queue Int Int Int (Vector a)` with a constructor pattern moves the fields: in place, but one heap cell per queue per step (counts and reuse): 17.7 s at 10^9, **6.4 times Roc and 2.4 times our own hamnth**. Only the flat form (fields as arguments, results as nested tuples: Elm tuples have at most 3 items, so `( ( f, b ), ( s, l ) )`) has no per element allocation. A record result would be copied (field access), a pattern on it is not possible; unboxed multi-value returns or record patterns in function heads would let the natural form run at the flat speed.
2. Algorithm: **Ficcus ours / Ficcus Roc algorithm (flat) = 2.83 (direct), 1.77 (stream)**; hand C 4.5 (16 B) or 3.2 (32 B); Rust 3.5 (16 B) or 2.4 (32 B).
3. Compiler: **Ficcus Roc algorithm (flat) / Roc = 0.94 (direct), 1.19 (CIS)**; against hand C with the same 32 byte element 1.47, against Rust 32 B 0.90. The 16 byte element (U16 counts) matters: C 1,257 against 1,775 ms, Rust 1,997 against 2,899, memory 34 against 66 MB; Ficcus has only 64 bit Int in a record (98 MB against Roc's 61).
4. The stream overhead per element (stream - direct): Ficcus flat 16.1 ns, Roc 13.0 ns, ours (hamnthstream) 25.7 ns. Stream / direct: Ficcus 7.2, Roc 5.7.
5. Gap to Roc 10^9 as asked (user's figures 2.765 s direct, about 17 s CIS; here 2.76 and 15.75): hamnth 6.96 (here 7.35) / 2.76 = 2.5-2.7; of it the algorithm is 2.83 and the compiler 0.94, i.e. **all of it is the algorithm**. hamnthstream 32.7 (here 33.0) / Roc CIS 15.75 = 2.1: algorithm 1.77, compiler 1.19.

## Conclusions
- Q1 (H15b): Ficcus running the Roc algorithm needs the flat encoding to show it: 2.60 s at 10^9 against Roc's 2.76 s (the gap to Roc was the algorithm, 2.83 times); as a stream 18.7 against 15.75 s. The compiler is not the cause of the direct gap; for streams it costs 1.19 times (3 allocations and a closure per element).
- Q2 (P1): the sepBy shape and the byte vector strings explain 6 to 8 % of A (0.7 of the 2.7 s gap to Roc; A2a alone 0.5 s); A2 is 1.36 times Roc (50 MB) and 1.31 (1 MB). The rest is closure and step allocation (833 M allocations, 929 M dups, 714 M drops against Roc's unboxed lambda sets). Rust: the shape is nothing (impl +1 %, dyn -3.5 %). Memory: A2 782 MB (8 bytes per byte for the string vectors and the input, capacity doubling of the arrays) against Roc 341.
## Caveats
Roc's timer has integer ms and excludes reading the file; Rust stage 1 - stage 0 differences are noise (negative). Rust strings stay `String` in the A2 Rust versions. The Ficcus A2 builds the step parser per item (as the Roc source); Rust builds it once. Counters come from separate builds (-DFIC_STATS). The tree of A2 differs (Vector arrays), so A2 vs A2a also contains Vector against cons list.
