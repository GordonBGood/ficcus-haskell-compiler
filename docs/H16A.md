# H16a: what known-function specialization and inlining could win on P1

Bench session, 18 Nov 2026. Branch `bench/h16a` (worktree `ficcus-haskell-compiler-h16a`, from `ficcus` at `2e5f3b16`), binary `bin/elmficA16`, **no compiler change**, shared files untouched, nothing committed or merged.
Machine: Ryzen 7 7840HS, gcc 16.2.1, rustc 1.100.0, load about 1, serial, `ulimit -v` 6 GB, median of 5 wall times (whole process), max RSS of one more run; parse = stage 2 - stage 1.
Files: `targets/p1/src/JsonS1.elm`, `JsonS2.elm`, `JsonS3.elm` (the three states, written by hand from `JsonCombV.elm` = A2; `JsonCombV.elm`, `JsonTreeV.elm`, `JsonCombS.elm` are copied from the H15b worktree, where they are untracked), `ficcus-tools/h16a_bench.py` (driver, derived from `p1b_bench.py`; `p1b_bench.py`, `h15b_try.sh` also copied), results `results/h16a/h16a_bench.json`, `run.log`, `perf_*.txt` (workspace root).
All five Ficcus versions print the checksum of `gen_json.py` on the 1 MB and the 50 MB document (`ok` in the JSON), same tree type (`JsonTreeV`), same generator and conversion.

## The three states (what was written)
- **S1**: every combinator application written out as a named function: `map`, `map2`, `andThen`, `keep`, `ignore`, `oneOf` (a chain of `case`, the library's flag logic kept), `lazy` (gone), `loop` (`stringBody`), `chompIf/While/Some`, `symbol`, `word`, `lexeme`, the `sepBy` step; `succeed` and all `\_ f -> f` lambdas are gone. Type `State -> Step a` with the heap `Step` and `State { src, offset }` is unchanged, the string loop still builds `More`/`Done`. The only function values left are `value` and `member` passed to `sepBy` (static closures of global functions: no closure is allocated; 1.9 M closures in 50 MB are the same as in the other versions).
- **S2**: S1 with the `Step` collapsed: a parser is `Vector Int -> Int -> R a`, `R a = { ok, c, v, o }` (a struct returned by value). Every `case f s of Good/Bad` of S1 is a field test on what the callee just returned. Bundled in this step (not separable here): (a) the Good/Bad cell is no longer allocated, (b) the state record is split into the source (a borrowed argument) and an Int offset, so `{ s | offset = .. }` no longer copies and counts the vector pointer, (c) the Bad message (a `String` that nothing reads except the final `Err`) is dropped, (d) `Loop` is the Bool in `v`, (e) `sepBy` is specialized per item (`sepByValue`, `sepByMember`): no function value remains. The commit flag `c` and the placeholder value of a Bad result remain.
- **S3**: S2 with `oneOf` unrolled into dispatch on the first byte (so no failed alternative is ever tried and the flags `c` vanish), results `( a, Int )` with offset -1 as failure (as JsonHand), the top level parsers (`minus`, `number`, `fraction`, `exponent`, `jword`, `jstring`, `jarray`, `jobject`, `member`, `value`) plain functions. `lexeme p` is still `p` then `spaces`, one function per combinator/rule. Behaviour differs from A2 only on invalid input (which alternative reports the error).

## Conclusions
1. **The first pass to build is the specialization of known function arguments plus inlining of the combinators (S1): 4.05 x (50 MB), 3.9 x (1 MB).** It removes the 170 M closures, the `oneOf` lists and most `fic_ap` calls, and cuts allocations 5 times (832 M to 158 M). It needs only what Stage (iii) already has (a specializer on constant function arguments of a known global; the `lazy` thunk and the lists are constants).
2. **The second is the collapse of `Step` (case of known constructor over an inlined or specialized callee, results returned as a struct): 2.4 x more.** This is where the allocations go from 158 M to 23 M (the remaining are the tree) and the dup/drop pairs of the state record. Its three bundled parts (no heap Good/Bad, state split, dropped message) were not measured separately; the dup/drop numbers (184 to 53 M) suggest the state split is a good part. A compiler would need: inlining of small functions returning a freshly built constructor, case of known constructor, and scalar replacement of a record that is only passed and returned (`{ src, offset }` with a Vector pointer).
3. **Unrolling `oneOf` by first byte and plain top level functions (S3) buy only 7 % (50 MB), 17 % (1 MB).** Not worth a pass; the dispatch by byte is a grammar-level optimisation (it needs the parsers' first sets), not a compiler one.
4. After S1 and S2 the combinator program is at 0.96 of JsonHand and 1.34 of Rust impl Fn; S3 is 0.90 of JsonHand. The remaining distance to Rust (1.26 to 1.34 x) is memory and tree: 22.8 M allocations (the tree), counts and the `Vector Int` input of 8 bytes per byte (783 against 357 MB).
5. The A2 profile says 48 % of the parse time is dup, drop and `fic_free_slow`, 15 % allocation: both are exactly what S1 and S2 remove (allocs -97 %, dups -94 %, drops -92 % from A2 to S2). Independently of the passes, `fic_free_slow` itself is a target (4 ns per death at 714 M deaths): a flat free for objects with no pointer children, no work list set up for them.

## Limits of the study
Hand written code is an upper bound: a compiler would not find S2's state split, or the message drop, without the corresponding analyses (dead field, scalar replacement), and S1's flag logic would stay. S1 used the exact library flag logic; real inlining would produce the same code. The ratios are measured on one grammar and one input family. The tree and checksums are the same in all versions. S3 changes error behaviour on invalid JSON (not tested).
